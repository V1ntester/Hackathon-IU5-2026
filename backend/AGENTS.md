# Правила работы с backend

## Обязательные ограничения пользователя

- Выполняй только текущее ТЗ. Сначала читай инструкции, код и существующие документы;
  не предполагай структуру по памяти. При неясности сначала изучи соответствующие файлы.
- Без прямой просьбы не создавай и не запускай тесты, сборки, серверы, контейнеры,
  миграции, линтеры, форматтеры и проверки, исполняющие код приложения. Не устанавливай
  зависимости и не скачивай модели/образы. Допустима проверка чтением и анализом diff.
- Не заявляй, что работа подтверждена запуском, если её проверяли только чтением.
  В результате перечисли изменения и оставшиеся ограничения проверки.
- Используй PostgreSQL, FastAPI, SQLAlchemy, Alembic и существующие локальные
  Qwen/Whisper. Не добавляй авторизацию, TTS, собственные ИИ-модели и новые технологии
  вне ТЗ. Новые зависимости требуют конкретного обоснования необходимости.
- Веса и ИИ-контейнеры уже подготовлены пользователем. Меняй их конфигурацию только
  по соответствующей задаче; наличие настройки не означает, что она применена к контейнеру.
- Анализ/проектирование не означает реализацию. Предлагаемое поведение явно отделяй
  от работающего кода. Не создавай дублирующих архитектурных документов: развивай
  `docs/Architecture_And_API.md`, поддерживай согласованность `docs/Backend.md`.
- Не перезаписывай `.env`, чужие изменения или индекс Git целиком. Не раскрывай
  секреты в выводе. Коммиты, слияния и публикации выполняй в рамках текущего задания.

## Принятая архитектура Python

Это правила данного репозитория, а не требование переделать весь существующий код.
Текущая структура: `main.py`, `dtos/`, `services/`, `models/`, `config.py`,
`database.py`, `requirements.txt`, `alembic.ini`. Миграции находятся в корневой
`migrations/`, указанной через `backend/alembic.ini`.

### Ответственность модулей

- `main.py`: создание FastAPI, lifespan, middleware, зависимости и тонкие HTTP/WS-
  обработчики. Обработчик принимает DTO, вызывает сервис и оформляет ответ.
  Не помещай сюда SQL, подбор знаний, историю диалогов и построение prompt.
- `dtos/`: Pydantic-модели HTTP/WS-контрактов и их валидация. Не смешивай их с ORM;
  не помещай сюда запросы к БД, HTTP-вызовы и бизнес-логику.
- `models/`: SQLAlchemy-модели и ограничения БД. Общий `Base` находится в
  `models/base.py`; экспортируй новые модели через `models/__init__.py`, чтобы
  Alembic увидел их метаданные. Модели не зависят от FastAPI, DTO и сервисов.
- `services/practice.py`: сценарий обработки реплики/аудио, координация сервисов,
  получение роли, истории и дополнительных сведений перед вызовом ИИ.
- `services/players.py`, `scenarios.py`: операции с игроками/статистикой и каталогом
  сценариев соответственно. Добавляй сервисы по конкретной ответственности.
- `services/ai_inference.py`: адаптер локальных ИИ-сервисов, httpx, сетевые таймауты,
  проверка ответа и лимиты параллельности. Не добавляй сюда ORM-запросы, выбор сценария
  и поиск знаний. Будущий метод генерации должен получать уже подготовленные сообщения.
- `services/sessions.py`: общая игровая сессия и синхронизация перемещений.
  История разговора с NPC — отдельная сущность, не часть этого класса.
- `config.py`: типизированные настройки из окружения. `database.py`: движок,
  фабрика AsyncSession и зависимости. Сохраняй единые источники настроек и Base.

Направление зависимостей: обработчики → сервисы → модели/инфраструктура.
DTO могут использоваться на границах сервисов. Модели не импортируют обработчики
и сервисы, а сервисы не импортируют `main.py`; циклических зависимостей быть не должно.
Не добавляй слои repositories, controllers,
универсальные фабрики и фреймворки без задачи, которая их оправдывает.

### Работа с данными и асинхронностью

- Используй типизацию аргументов/результатов, понятные имена, async SQLAlchemy/httpx;
  не блокируй event loop синхронными сетевыми операциями.
- Один AsyncSession принадлежит одному запросу/задаче; не дели его между конкурентными
  coroutine. Общий HTTP-клиент и общие семафоры создавай через lifespan.
- Явно определяй владельца транзакции. В составной операции связанные изменения
  фиксирует координирующий сервис; вспомогательный метод не должен неожиданно делать
  commit. В текущем PlayerService счётчики делают commit — учти это при расширении
  диалога, а не считай сохранение истории и статистики автоматически атомарным.
- Не держи транзакции и блокировки строк PostgreSQL во время ожидания LLM. Нужные
  данные копируй до rollback/закрытия сессии; учитывай истечение ORM-атрибутов.
- Для новых таблиц нужны Alembic-миграции, внешние ключи и ограничения. Не подменяй
  миграции вызовом `create_all()` и не переписывай уже применённую начальную миграцию.
- UUID игрока, UUID диалога, UUID обмена и ID сценария обозначают разные сущности.
  Сохраняй совместимость типов внешних ключей с существующими моделями.
- Счётчики увеличивай атомарно. Для повторов HTTP и одновременных запросов явно
  определяй идемпотентность и порядок обработки; семафор LLM не заменяет порядок
  реплик внутри одного диалога.
- Сохраняй действующие контракты либо описывай миграцию клиента. При RAG история
  берётся с сервера, фильтруется по диалогу/игроку/сценарию и ограничивается токенами.
  UUID и прочие служебные поля не превращаются автоматически в текст для LLM.

## Перед завершением задачи

Прочитай изменённые файлы и вызывающие места, сопоставь DTO, сервисы, модели,
миграции, конфигурацию и документацию. Не запускай запрещённые проверки.
Если состояние ветки изменилось, не откатывай его к запомненному ранее состоянию.
Не считай план из архитектурного документа уже реализованной функцией.
