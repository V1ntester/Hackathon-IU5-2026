# Устройство и работа фронтенда

## Как запустить фронтенд локально

Нужны установленные Node.js и npm, совместимые с Vite 7. Команды ниже предназначены
для самостоятельного выполнения в PowerShell. Backend и фронтенд запускаются
отдельно и работают в двух открытых терминалах.

### 1. Запустить backend для сетевой игры

Если Python-окружение, PostgreSQL и миграции ещё не подготовлены, сначала выполните
инструкцию [Backend.md — подготовка и запуск](Backend.md#подготовка-и-запуск-вручную).
Для уже подготовленного backend откройте первый терминал в корне проекта:

```powershell
cd D:\my-games\Hackathon-IU5-2026
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 0.0.0.0 --port 8000 --workers 1 --ws-max-size 4096
```

Оставьте этот терминал открытым. PostgreSQL нужен для создания гостя, Qwen — для
ответов NPC, Whisper — для голосового ввода с микрофона. Уже работающие контейнеры
ИИ повторно скачивать или пересоздавать не нужно.

### 2. Установить зависимости и запустить фронтенд

Во втором терминале перейдите именно в папку `web`, где находится `package.json`:

```powershell
cd D:\my-games\Hackathon-IU5-2026\web
npm.cmd install
npm.cmd run dev
```

`npm.cmd install` нужен при первой подготовке или изменении зависимостей; при
последующих запусках достаточно `npm.cmd run dev`. Установка скачивает библиотеки
фронтенда, а не веса моделей. Нчёча Windows используется `npm.cmd`, чтобы политика
PowerShell для скриптов не мешала запуску npm. В других оболочках можно использовать `npm`.
Пути в примерах соответствуют текущему расположению репозитория; при другом
расположении замените их на свои.

### 3. Открыть игру

Откройте в браузере **[http://127.0.0.1:5173](http://127.0.0.1:5173)**.
Нажмите «Войти»: WASD — движение, мышь — обзор, Shift — бег, Esc — пауза.
Рядом с NPC в офисе нажмите E для открытия разговора. Клиент отправит «Привет»
в LLM и покажет ответ рекрутера. Enter отправляет сообщение, Shift+Enter добавляет
новую строку. Кнопки отправки нет.
При загрузке сайт запрашивает доступ к микрофону. Иконка справа от поля начинает
запись; повторное нажатие или 20 секунд завершают её. После распознавания текст
вставляется в поле, а отправляется NPC только по Enter.
Статус сети и число игроков показаны в углу экрана.
Для нескольких игроков можно открыть этот же адрес в двух вкладках: каждая
получит отдельного гостя. Это инструкция для ручного использования, а не результат
уже проведённой проверки.

Фронтенд обращается к FastAPI через встроенный dev-прокси: `/api` и `/ws`
пересылаются на `http://127.0.0.1:8000`. Для стандартного запуска создавать
`web/.env` не требуется. Если backend находится по другому адресу, скопируйте
`web/.env.example` в `web/.env`, задайте `BACKEND_PROXY_TARGET` и перезапустите Vite.
Подробности прямого подключения и сборки — в разделе [Адреса и настройка](#адреса-и-настройка).

Для остановки нажмите **Ctrl+C** в соответствующем терминале.

### Если не получается открыть или подключиться

| Что видно | Что сделать |
| --- | --- |
| `npm`/`npm.cmd` не найден | Установить Node.js с npm и открыть новый терминал |
| npm сообщает об отсутствии `package.json` | Перейти в папку `web`, затем повторить команду |
| Vite сообщает о неподдерживаемой версии Node.js | Использовать версию Node.js, указанную в сообщении Vite как совместимую |
| Порт 5173 занят | Остановить ранее запущенный экземпляр фронтенда; `strictPort` не позволяет автоматически выбрать другой порт |
| Офис открылся, но сервер недоступен | Проверить, что FastAPI запущен на порту 8000 и PostgreSQL доступен; ошибки backend видны в первом терминале |
| Нет ответа NPC | Проверить работающий Qwen и сообщение в панели |
| Модели комнаты не появились | Проверить загрузку GLB из `web/public/assets/`; ошибки импорта выводятся в консоль браузера |

Для просмотра только офисной сцены backend не обязателен: фронтенд откроется,
но синхронизация игроков и диалог NPC будут недоступны.

## Фактический стек и границы

Фронтенд находится в `web/`: TypeScript 5.9.3, Vite 7.3.7,
`@babylonjs/core` 8.56.2 и `@babylonjs/loaders`. В исходном ТЗ указан Three.js,
но существующая реализация использует Babylon.js. При интеграции движок сохранён;
новые технологии и зависимости не добавлены. Для сети используются браузерные
`fetch`, `WebSocket` и `FormData`.

Клиент отображает офис, управляет локальной камерой, показывает других игроков
и диалог NPC. Общая архитектура и контракт сервера описаны в
[Architecture_And_API.md](Architecture_And_API.md), подготовка backend — в [Backend.md](Backend.md).

## Состояние и управление

Отдельного глобального хранилища нет. `Game` связывает экземпляры компонентов:

- Локальная позиция и направление находятся в `UniversalCamera` контроллера.
  Скорость, нажатые клавиши и признак активности хранятся в `FirstPersonController`.
- UUID гостя и WebSocket принадлежат `GameClient`; они живут до закрытия/перезагрузки
  страницы. Две вкладки создают разные профили и могут играть одновременно.
- Чужие игроки находятся в `Map` класса `RemotePlayers`, по одному аватару на UUID.
- Поля диалога, сообщения текущего собеседования и ожидание ответа принадлежат
  `NpcDialogPanel`. В UI используется сценарий `interview`; постоянного хранения
  истории на backend и передачи этой истории LLM пока нет.

`Office` создаёт помещение 26 × 26 м. Камера появляется в `(0, 1.7, 0)` и смотрит
вдоль +Z. Система координат Babylon по умолчанию сохранена: Y направлен вверх.
Позиция в сетевом протоколе — положение глаз, не стоп. Тело удалённого игрока
сдвигается вниз от этой позиции на половину высоты 1.7 м.

Для входа пользователь кликает по заставке: браузер захватывает курсор, контроллер
включается. WASD/стрелки перемещают, Shift включает бег, мышь меняет обзор.
Каждый кадр контроллер рассчитывает горизонтальное смещение с плавным ускорением
и торможением; Babylon обрабатывает коллизии камеры с офисом и гравитацию.
FOV немного увеличивается при беге. Отдельной системы покачивания камеры в коде нет.
Esc освобождает курсор и показывает паузу. Потеря фокуса окна очищает нажатые клавиши.
Во время паузы и ввода в элементы формы движение не накапливается.

Разговор с NPC открывается по E рядом с ним в офисе (радиус 2.6 м).
`InteractionController` открывает `NpcDialogPanel`, отключает движение и освобождает
курсор. Esc или кнопка закрытия отменяют запись и ожидающий запрос и возвращают
управление игроку. Сцена при разговоре не меняется.

Дверь кабинета — отдельное взаимодействие: E переключает сцену через `SceneManager`
и открывает только `InterviewPanel`. Сейчас это заглушка с сообщением о временной
недоступности собеседования и кнопкой возврата в офис. LLM и микрофон из заглушки
не вызываются. Пока открыта любая из этих панелей, открыть другую нельзя.

## Подключение и синхронизация

1. При создании `Game` клиент отправляет `POST /api/players` с именем `Гость`.
   Подключение начинается при загрузке страницы, независимо от клика «Войти».
2. Полученный UUID используется для `/ws/{player_id}`. На открытии соединения
   отправляется позиция камеры; статус передаётся панели собеседования. Каталог
   `/api/scenarios` остаётся доступным API, но текущая панель использует `interview`.
3. Таймер каждые **80 мс** передаёт JSON `move` с `position: {x,y,z}` и `rotation_y`.
   Это реже серверного ограничения 50 мс. Позиция отправляется и при остановке,
   чтобы финальное положение не терялось; поворот нормализуется к [-π, π].
4. При закрытом сокете или непустом буфере WebSocket отправка пропускается;
   следующий тик отправит актуальные координаты. Очередь устаревших движений не создаётся.
5. Сообщение `state` содержит полный массив `players`. Собственный UUID исключается
   из отображения: серверный снимок не переставляет локальную камеру.
6. Новые удалённые игроки получают капсулу и небольшой указатель направления.
   Позиция и поворот плавно приближаются к последним сетевым значениям каждый кадр;
   для поворота выбирается кратчайшая дуга. Коллизий между аватарами нет.
7. Игроки, отсутствующие в следующем полном снимке, удаляются. При обрыве сети
   все чужие аватары очищаются, статус меняется и через 2 секунды выполняется
   повторная попытка подключения с тем же UUID. Локальная позиция сохраняется.

Начальное состояние сервера содержит нулевую позицию до первого `move`; клиент
заменяет её отправкой позиции камеры. Номера снимков `revision` могут иметь
пропуски и сбрасываются после рестарта backend. Клиент обрабатывает снимки по
порядку WebSocket и не требует непрерывных номеров.

## NPC: LLM и голосовой ввод

При открытии `NpcDialogPanel` отправляется `POST /api/ai/chat` с `player_id`,
`scenario_id=interview`, `message=Привет`. Если сервер ещё не подключён, панель
дожидается соединения. Приветствие не повторяется при обычном переподключении
после успешного ответа; новое открытие разговора с NPC начинает новый диалог.
Перед приветствием загружается название сценария из `/api/scenarios` — им
подписываются реплики собеседника. Поле ввода и микрофон появляются только после
первого успешного ответа. При ошибке доступна кнопка повтора приветствия.

Дальнейшие сообщения отправляются по Enter, Shift+Enter сохраняет стандартный
перенос строки. Пустые сообщения, повтор клавиши и Enter при IME-композиции
не отправляются. Лимит — 1000 символов. Отдельной кнопки отправки нет.
После Enter поле немедленно очищается, а сообщение игрока появляется в ленте.
Над вводом сразу создаётся реплика сценария «Готовит ответ…»: по завершении
её текст заменяется ответом сервера без добавления второго сообщения. При ошибке
в этой реплике показывается ошибка, а исходный черновик возвращается в поле.
Поле фиксировано на две строки высоты, длинный текст прокручивается внутри.
Внешний текст выводится через `textContent`.
Это история отображения в браузере, а не RAG: backend ещё не передаёт её LLM.

При создании интерфейса запрашивается доступ к микрофону; поток сразу
останавливается без записи. В поддерживающем браузере нужен HTTPS либо
localhost/127.0.0.1. Отказ или отсутствие микрофона не отключают текстовый ввод.

Микрофон расположен справа от textarea, на кнопке только SVG-значок. Первое
нажатие запускает MediaRecorder, повторное или таймер 20 секунд останавливают его.
Выбирается поддерживаемый формат WebM/Opus, WebM, Ogg/Opus или MP4. После остановки
все аудиотреки выключаются, файл отправляется в `/api/ai/transcribe` multipart-полями
`player_id`, `file`, `language=ru`. Браузер сам формирует boundary.

Расшифровка заменяет содержимое поля, но не отправляется NPC автоматически.
Игрок исправляет её и нажимает Enter. Пустой результат или ошибка не стирают
прежний ввод; для текста длиннее 1000 символов показывается просьба сократить его.
Во время запроса и записи ввод блокируется, кнопка остановки записи доступна.
Выход, разрыв соединения и dispose отменяют операцию; поздний результат не попадает
в новый диалог. Клиентская отмена запроса не гарантирует остановку уже начатых
вычислений на сервере. Новых зависимостей и выбора готового аудиофайла нет.

Клиент никогда не обращается напрямую к Qwen, Whisper или PostgreSQL.
`GET /api/players/{player_id}/stats` остаётся доступным API, но экрана статистики
во фронтенде сейчас нет.

## Адреса и настройка

По умолчанию HTTP и WebSocket используют origin открытой страницы. Для разработки
в `vite.config.ts` настроены прокси `/api` и `/ws` на `http://127.0.0.1:8000`.
Vite слушает `127.0.0.1:5173`, `strictPort` запрещает незаметный переход на другой
порт, который не разрешён в `CORS_ORIGINS` backend.

В `web/.env.example` описаны две необязательные настройки:

| Переменная | Назначение |
| --- | --- |
| `BACKEND_PROXY_TARGET` | Куда dev-сервер Vite пересылает `/api` и `/ws`; по умолчанию `http://127.0.0.1:8000` |
| `VITE_BACKEND_URL` | Полный origin backend, например `http://localhost:8000`; пустое значение оставляет доступ через origin страницы |

Для изменения настроек пример можно скопировать в `web/.env`. Команды npm
выполняются из `web/`; поэтому Vite читает окружение из этой папки.
`VITE_BACKEND_URL` встраивается при сборке; протокол `ws:`/`wss:` определяется по
`http:`/`https:` адреса backend. При прямом доступе origin фронтенда должен быть
разрешён в `CORS_ORIGINS`, включая WebSocket. На HTTPS-странице нужен HTTPS/WSS backend.

Существующие команды проекта: `npm run dev`, `npm run build`, `npm run preview`.
Dev-прокси действует только для `npm run dev`. Для готовой сборки и preview нужно
задать `VITE_BACKEND_URL` до сборки либо настроить внешний reverse proxy `/api` и
`/ws` на FastAPI. Статические файлы обслуживаются отдельно от FastAPI.
Привязка dev-сервера к 127.0.0.1 предназначена для работы на одном компьютере;
доступ с других компьютеров требует отдельной настройки хоста и разрешённых origin.

При остановленном backend офис остаётся доступен локально; статус показывает
ошибку, клиент повторяет подключение, NPC недоступен. Код не подтверждает успешный
вход на сервер одним только захватом курсора: сетевой статус отображается отдельно.

При `Game.dispose()` закрываются сокет и HTTP-запросы, очищаются таймеры и слушатели,
удаляются чужие аватары, панели, камера, сцена и движок. Это также используется
обработчиком HMR в `main.ts`.

## Проверка документации

Описание составлено по фактическим исходникам и сверено с контрактами FastAPI.
Во время выполнения интеграции зависимости не устанавливались, сборка, серверы,
тесты и сетевые запросы к сервисам не запускались. Критерии работы в нескольких
браузерах требуют отдельной проверки запуском; этот документ не заявляет её результат.

## События backend → frontend

Backend может отправлять по существующему WebSocket `/ws/{player_id}` сообщения
двух видов: снимки `state` и события `event`. Общий DTO `ServerEvent` находится
в `backend/dtos/event.py`; его TypeScript-аналог и проверка формы —
в `web/src/network/ServerEvent.ts`.

```json
{"type": "event", "name": "example", "payload": {"object_id": "office-light"}}
```

`type` всегда равен `event`, `name` — имя события (1–100 символов),
`payload` — JSON-объект, по умолчанию `{}`. Конкретные успешные игровые события пока не определены; `example` здесь только пример формата.

Из асинхронной бизнес-операции можно отправить событие одному игроку:

```python
await session_service.send_event(
    player_id, ServerEvent(name="example", payload={"object_id": "office-light"})
)
```

Для всей сессии: `await session_service.broadcast_event(event)`.
`send_event` возвращает `False`, если игрок не подключён или отправка не удалась.
События отправляются напрямую, отдельно от заменяемых снимков состояния;
отправка события и снимка одному клиенту выполняется последовательно.
Таймаут отправки — 5 секунд, при ошибке соединение закрывается с кодом 1011.
Хранения событий, подтверждения обработки и повторной доставки после переподключения нет.

`GameClient` проверяет конверт события и вызывает необязательный callback
`event: (event: ServerEvent) => void`, переданный в конструктор. При отсутствии
callback событие игнорируется. `Game` отображает ошибку `command_rejected`
для света; успешное переключение применяется через снимок `state`.
Снимки `state` обрабатываются как раньше.

### interact на frontend

`GameClient.sendInteract(objectId)` отправляет:

```json
{"type": "interact", "object_id": "office-light"}
```

Метод возвращает `true`, когда сообщение передано WebSocket, и `false`, если
соединение закрыто или занято отправкой; это не подтверждение обработки backend.
Пустой идентификатор или строка длиннее 100 символов вызывают ошибку.
Нажатие E рядом с выключателем отправляет `interact` для `office-light`. Backend записывает
`last_interaction_object_id` в состояние участника. Команда `interact` пока
не создаёт отдельного события при успехе; неизвестный ID возвращает
`command_rejected` с кодом `object_not_found`.

## Синхронизация света в лобби

При создании серверной сессии `office-light` имеет состояние `active` — свет включён.
Клиентская сцена также начинает с включённым светом до первого снимка сервера.
Общий `WorldObject` по умолчанию остаётся `inactive`; начальное состояние света
задаётся явно в `SessionService`.

E рядом с выключателем отправляет `{"type":"interact","object_id":"office-light"}`.
Сервер переключает `active` ↔ `inactive` и рассылает `state.objects` всем участникам.
`GameClient` проверяет объекты и вызывает callback `objects`; `Game` применяет
состояние через `Office.setLightEnabled`, обновляя освещение и эмиссию панелей.
Локального переключения до ответа сервера нет; повторные снимки не меняют
уже применённое состояние. Если соединение недоступно или занято отправкой,
клиент показывает ошибку, повторить действие можно нажатием E.

Новый или переподключившийся игрок получает текущий свет из первого снимка,
даже если его выключил другой участник. Отключение всех игроков не сбрасывает
объекты. После перезапуска backend свет снова включён; состояние хранится в памяти,
миграция БД не требуется. Неизвестный ID возвращает событие `command_rejected`
с кодом `object_not_found`, сохраняя WebSocket открытым.

Для разработки запускайте backend из корня проекта с автоматической перезагрузкой:

```bash
python -m uvicorn backend.main:app --host 0.0.0.0 --port 8000 --workers 1 --ws-max-size 4096 --reload --reload-dir backend
```

При перезагрузке процесса сессия сбрасывается, клиенты переподключаются. Без
`--reload` после изменений backend требуется ручной перезапуск, иначе старый
процесс может не поддерживать актуальные команды клиента.

## Панель управления объектами

Отдельная административная страница доступна по адресу `http://127.0.0.1:5173/admin/`.
Она загружает `/api/admin/objects`, показывает состояния объектов и позволяет задать
`active` или `inactive`. Список обновляется каждые 2 секунды, чтобы отображать
переключения, сделанные игроками. Сборка Vite включает страницу отдельно от игры.
При размещении frontend на другом origin добавьте его в `CORS_ORIGINS` backend;
backend разрешает методы `GET`, `POST` и `PUT`. Административная авторизация пока
не настроена, поэтому используйте панель только в доверенной сети.

В админской панели раздел «Подключения» показывает активных игроков, время входа,
последний ping и FPS. Клиент отвечает на серверный heartbeat; RTT обновляется
примерно раз в 5 секунд, а список панели — каждые 2 секунды. FPS снимается Babylon.js и отправляется раз в 2 секунды. Если отчёт старше
10 секунд, API возвращает `null` и панель показывает прочерк.

## Подключение друзей по локальной сети

Vite слушает все сетевые интерфейсы, поэтому игру можно открыть с других устройств
по адресу `http://<IP-компьютера>:5173`. Узнайте IPv4-адрес компьютера в локальной
сети (в Windows: `ipconfig`; нужен адрес Wi-Fi/Ethernet, например `192.168.1.25`),
запустите backend и Vite и разрешите входящие TCP-подключения к порту 5173 в
брандмауэре Windows. Backend остаётся за Vite-прокси на `127.0.0.1:8000`.

Для WebSocket в корневом `.env` должна быть включена настройка
`ALLOW_LAN_WEBSOCKET_ORIGINS=true`. Она разрешает только HTTP-origin с приватным
IP и портом 5173; localhost продолжает работать. После изменения корневого `.env` перезапустите
backend.

При запуске в WSL2 с NAT настройте Windows port forwarding. В PowerShell,
запущенном от имени администратора, выполните после старта Vite:

```powershell
$wslIp = (wsl hostname -I).Trim().Split()[0]
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=5173 connectaddress=$wslIp connectport=5173
New-NetFirewallRule -DisplayName "Office Vite LAN" -Direction Inbound -Protocol TCP -LocalPort 5173 -Action Allow -Profile Private
```

Узнайте IPv4-адрес Wi-Fi/Ethernet компьютера командой `ipconfig`, например
`192.168.1.25`, и передайте друзьям `http://192.168.1.25:5173`.
После перезапуска WSL его IP может поменяться: обновите portproxy правилом
`netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=5173`
и выполните команду добавления снова. Если в WSL включён mirrored networking,
portproxy обычно не нужен; firewall всё равно должен разрешать TCP 5173.
Панель `/admin/` доступна по тому же сетевому адресу.
