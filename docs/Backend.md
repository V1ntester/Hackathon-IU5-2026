# Backend игрового сервера

## Выбор БД и данные

Используется **PostgreSQL**: транзакции, внешние ключи и конкурентные обновления
подходят для многопользовательского сервера и позволяют сохранять статистику без
потери при одновременных запросах. Асинхронный драйвер — `asyncpg`, работа с данными
— SQLAlchemy 2.0. Alembic управляет схемой; приложение не создаёт таблицы при запуске.

Таблицы:

| Таблица | Содержимое |
| --- | --- |
| `users` | UUID гостя, отображаемое имя, время создания UTC |
| `player_stats` | Число подключений, успешных запросов к Qwen и успешных распознаваний Whisper; одна запись на гостя |
| `scenarios` | Идентификатор, название, описание и системная инструкция NPC |

Первая миграция создаёт таблицы и сценарий `interview`. Счётчики увеличиваются
атомарными SQL-обновлениями. Ошибки ИИ не увеличивают статистику.
Счётчик распознаваний учитывает успешный ответ сервиса, включая пустой текст при тишине.
Координаты находятся в памяти: при подключении сервер начинает с нулевой позиции
до первого `move`; клиент сразу передаёт актуальное положение своей камеры.
Аудио не сохраняется в постоянное хранилище. Временный буфер загрузки управляется FastAPI.

## Подготовка и запуск вручную

Ниже команды для самостоятельного выполнения из корня репозитория в PowerShell.
Во время разработки backend установка, миграции, запуск и тесты не выполнялись.
Контейнеры Qwen и Whisper уже работают; скачивать их образы или веса повторно не нужно.

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
Copy-Item .env.example .env
```

В `.env` задайте параметры PostgreSQL и `DATABASE_URL` в формате
`postgresql+asyncpg://USER:PASSWORD@HOST:PORT/DATABASE`. Для пароля со специальными
символами используйте URL-кодирование в строке подключения. Значения `game` в примере
предназначены для локальной разработки. База должна существовать до применения миграций.
В текущем Compose порт PostgreSQL на хосте — **5435**, внутри контейнера — 5432;
в `.env.example` указан адрес хоста `localhost:5435`.

Если PostgreSQL ещё не подготовлен, в `docker-compose.yaml` добавлен сервис `db` с
постоянным томом `postgres_data`. Запуск только БД, не затрагивающий ИИ-сервисы:

```powershell
docker compose up -d db
```

Эта команда при отсутствии образа PostgreSQL скачает его; уже работающие ИИ-модели
не скачиваются. Можно вместо Docker использовать существующий сервер PostgreSQL,
указав его адрес в `.env`. Переменные `POSTGRES_*` применяются контейнером только
при первой инициализации пустого тома. После готовности БД:

```powershell
.\.venv\Scripts\alembic.exe -c backend/alembic.ini upgrade head
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 0.0.0.0 --port 8000 --workers 1 --ws-max-size 4096
```

Запускайте **один процесс**: игровой мир и список WebSocket-подключений находятся
в его памяти. Несколько процессов потребуют общего слоя обмена состоянием, которого
в текущем ТЗ нет. PostgreSQL хранит данные независимо от перезапусков backend.

После запуска описание HTTP API доступно по адресу `http://localhost:8000/docs`.
`CORS_ORIGINS` — JSON-массив адресов фронтенда с протоколом и портом без завершающего `/`.
Он используется также для проверки заголовка `Origin` WebSocket. Клиенты без `Origin`
могут подключаться. Backend работает на хосте, поэтому ИИ-сервисы доступны через localhost.

## Модель NPC: Qwen3-4B-Instruct-2507

Docker Compose настроен на **Qwen3-4B-Instruct-2507 в квантизации Q4_K_M**.
Файл весов занимает около **2,5 ГБ**; для работы дополнительно нужна память
под контекст и вычисления.

- [Страница весов Qwen3-4B-Instruct-2507-Q4_K_M.gguf](https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF/blob/main/Qwen3-4B-Instruct-2507-Q4_K_M.gguf).
- [Прямая ссылка на скачивание GGUF](https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF/resolve/main/Qwen3-4B-Instruct-2507-Q4_K_M.gguf).
- [Официальное описание модели](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507).

Начальные настройки рассчитаны на локальную работу на Ryzen 7 8845HS с 16 ГБ RAM:

| Параметр | Значение |
| --- | --- |
| Файл на хосте | `models/llm/Qwen3-4B-Instruct-2507-Q4_K_M.gguf` |
| Файл в контейнере (`-m`) | `/models/Qwen3-4B-Instruct-2507-Q4_K_M.gguf` |
| Имя модели в API (`--alias`, `QWEN_MODEL`) | `Qwen3-4B-Instruct-2507` |
| Контекст (`-c`) | 4096 токенов |
| Потоки CPU (`-t`) | 6 |
| Слоты генерации (`--parallel`) | 1 |
| GPU-слои (`-ngl`) | 0, вычисления на CPU |
| Максимальный ответ NPC (`max_tokens` в backend) | 192 токена |

Backend допускает один одновременный запрос к Qwen; остальные ожидают освобождения
семафора. Это ограничивает нагрузку, сохраняя возможность подключения нескольких
игроков. Для Whisper остаётся до двух одновременных запросов. Скорость генерации
на конкретном компьютере запуском не измерялась.

### Замена ранее установленной модели

1. Из корня проекта скачайте файл по указанной ссылке либо выполните в PowerShell:

   ```powershell
   New-Item -ItemType Directory -Force -Path models\llm
   curl.exe -fL --retry 3 -o models\llm\Qwen3-4B-Instruct-2507-Q4_K_M.gguf "https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF/resolve/main/Qwen3-4B-Instruct-2507-Q4_K_M.gguf"
   ```

   Старый GGUF можно оставить в той же папке: Compose загружает только файл из `-m`.
   Веса не добавляются в Git. Интернет нужен для скачивания, дальнейшая работа локальная.

2. В существующем корневом `.env` замените строку имени модели:

   ```dotenv
   QWEN_MODEL=Qwen3-4B-Instruct-2507
   ```

   Для нового окружения правильное значение уже есть в `.env.example`.
   Не перезаписывайте существующий `.env` целиком: в нём находятся настройки БД.
   `QWEN_MODEL` должен совпадать с `--alias` сервиса `llm`.

3. После завершения скачивания примените новую конфигурацию только к LLM:

   ```powershell
   docker compose up -d --no-deps --force-recreate --pull never llm
   ```

   Команда использует имеющийся образ llama.cpp, не запускает и не пересоздаёт
   PostgreSQL или Whisper. Обычный `docker compose restart llm` не применяет
   изменения аргументов контейнера.

4. Перезапустите FastAPI обычной командой из раздела подготовки: backend должен
   перечитать `.env`, новое имя модели и ограничения генерации.

Контекст 4096 — доступный бюджет модели на запрос. Текущий backend передаёт
системную инструкцию и одну реплику; история разговора автоматически не добавляется.
Обновление весов и контекста не меняет это поведение.

## HTTP API

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/players` | Создать гостя и нулевую статистику |
| `GET /api/players/{player_id}/stats` | Получить статистику гостя |
| `GET /api/scenarios` | Получить сценарии без внутренних инструкций NPC |
| `POST /api/ai/chat` | Получить текстовый ответ NPC |
| `POST /api/ai/transcribe` | Получить текст из аудиозаписи |

Создание гостя: JSON `{"display_name":"Игрок"}`. Имя — 1–40 символов после удаления
пробелов по краям. Возвращается HTTP 201 и объект с `id`, `display_name`, `created_at`.
Без имени используется `Гость`. Фронтенд хранит `id` в памяти страницы и использует
его для WebSocket и запросов к ИИ. Переподключение использует тот же профиль;
новая вкладка или перезагрузка страницы создаёт другого гостя.

Запрос Qwen:

```json
{
  "player_id": "UUID из ответа создания гостя",
  "scenario_id": "interview",
  "message": "Я занимался разработкой командного проекта."
}
```

Ответ: `{"reply":"Текст NPC"}`. Сообщение — 1–1000 символов. Сервер передаёт
системную инструкцию сценария и текущую реплику в
`http://localhost:8081/v1/chat/completions`, без потоковой выдачи, с ограничением
ответа в 192 токена. История диалога на этом этапе не сохраняется и не пересылается.
Модель задаётся переменной `QWEN_MODEL`.

Распознавание: `multipart/form-data`, поля `player_id` и `file` (аудиозапись),
необязательное `language`: `auto` (по умолчанию) или `ru`.
Лимит аудиофайла по умолчанию 10 МиБ (`MAX_AUDIO_BYTES`). Принимаются MIME-типы
`audio/wav`, `audio/x-wav`, `audio/wave`, `audio/webm`, `video/webm`, `audio/ogg`,
`audio/mpeg`, `audio/mp4`, `audio/flac`, включая параметры кодека после `;`.
Например, запись MediaRecorder можно передать как `audio/webm;codecs=opus`.
WAV дополнительно проверяется по заголовку RIFF/WAVE; декодирование и проверку
остальных форматов выполняет Whisper. Конвертация браузерных форматов использует
уже указанный в Docker-конфигурации Whisper флаг `--convert` и требует поддержки
конвертации внутри его образа; WAV можно передавать напрямую.
Backend передаёт файл в `http://localhost:8082/inference`, с `response_format=json`
и выбранным языком. Микрофон фронтенда передаёт `ru`.
Возвращается `{"text":"Распознанный текст"}`; фронтенд вставляет результат в поле,
а игрок отправляет его в `/api/ai/chat` отдельным нажатием Enter.
Пустой текст означает, что речь не распознана; отправлять его в чат не нужно.

Ошибки: 404 — неизвестный игрок или сценарий; 413 — слишком большой аудиофайл;
415 — неподдерживаемый формат или неверный заголовок WAV; 422 — неверные поля запроса
или пустой файл; 502 — ИИ недоступен или вернул
неверный ответ; 504 — превышен таймаут ИИ (`AI_TIMEOUT_SECONDS`, по умолчанию 120 секунд
для сетевых операций). К Qwen допускается один одновременный запрос, к Whisper — до двух;
остальные ожидают свободного места. Ожидание места не входит в сетевой таймаут.

## WebSocket и браузерный клиент

Фактический фронтенд расположен в `web/` и использует Babylon.js, TypeScript и Vite.
Three.js из исходного ТЗ не используется. Устройство клиента и настройка прокси
описаны в [Frontend.md](Frontend.md), общая архитектура — в
[Architecture_And_API.md](Architecture_And_API.md).

После создания гостя открыть `ws://localhost:8000/ws/{player_id}`. Для HTTPS использовать
`wss://`. Одновременно допускается одно соединение на гостя; повторное соединение
отклоняется, не отключая первое. Несуществующие гости также отклоняются.

После входа, принятого движения, взаимодействия с объектом или выхода игрока сервер рассылает всем
полный снимок общего мира:

```json
{
  "type": "state",
  "revision": 1,
  "objects": [{"id": "office-light", "state": "active"}],
  "players": [
    {
      "id": "UUID игрока",
      "display_name": "Игрок",
      "position": {"x": 0.0, "y": 0.0, "z": 0.0},
      "rotation_y": 0.0,
      "last_interaction_object_id": null
    }
  ]
}
```

Фронтенд заменяет локальный список игроков содержимым `players`; отсутствующие в снимке
игроки вышли. Собственного игрока определяет по UUID. `revision` возрастает в пределах
работы процесса. Для медленных клиентов ожидающий снимок заменяется свежим, поэтому
пропуски номеров нормальны. Отправка имеет таймаут 5 секунд и не блокирует других игроков.

Клиент передаёт только собственные координаты и поворот, без идентификатора игрока:

```json
{
  "type": "move",
  "position": {"x": 1.5, "y": 0.0, "z": -2.0},
  "rotation_y": 1.57
}
```

Координаты соответствуют осям сцены Babylon.js: Y вверх, yaw=0 направлен вдоль +Z.
Передаётся позиция камеры (глаз), поворот вокруг Y — в радианах.
Координаты ограничены диапазоном ±10000, поворот — приблизительно ±2π;
NaN и бесконечности запрещены. Сервер принимает движения не чаще 20 раз в секунду
от одного игрока, более частые сообщения игнорируются. Фронтенду следует отправлять
движения с интервалом не менее 50 мс, включая финальную позицию после остановки.
Физика, коллизии и проверка скорости в текущий backend не входят.
Текущий клиент отправляет позицию каждые 80 мс, нормализует поворот к диапазону
[-π, π] и отображает других игроков по снимкам, плавно обновляя их аватары.

Некорректное сообщение или бинарный кадр закрывают соединение с кодом 1008;
слишком длинное сообщение — 1009. При разрыве соединения игрок удаляется из мира,
остальные получают новый снимок. Профиль и статистика остаются в PostgreSQL.
Нулевые координаты сервера действуют до первого сообщения `move`; текущий клиент
сразу после соединения отправляет положение камеры. После сетевого переподключения
локальная камера сохраняет положение, повторная попытка выполняется через 2 секунды.

## Границы реализации

Авторизации нет: UUID идентифицирует гостя, но не подтверждает право доступа к нему.
Фронтенд подключён к этому API: гостевой вход, синхронизация перемещений и текстовый
диалог с NPC в офисе (`NpcDialogPanel`): приветствие через LLM, отправка по Enter и запись
голоса до 20 секунд с вставкой расшифровки в поле. Прикрепления готового файла нет.
RAG, TTS, собственные модели, оценивание ответов, боты и полный игровой цикл не реализованы.
Используются существующие Qwen и Whisper.

## Синхронизация света в лобби

При создании серверной сессии `office-light` имеет состояние `active` — свет включён.
Клиентская сцена также начинает с включённым светом до первого снимка сервера.
Общий `WorldObject` по умолчанию остаётся `inactive`; начальное состояние света
задаётся явно в `SessionService`.

E рядом с выключателем отправляет `{"type":"interact","object_id":"office-light"}`.
Сервер переключает `active` ↔ `inactive` и рассылает `state.objects` всем участникам.
`GameClient` проверяет объекты и вызывает callback `objects`; `Game` применяет
состояние через `Office.setLightEnabled`, обновляя освещение и эмиссию панелей.
Локального переключения до ответа сервера нет; повторные снимки не меняют
уже применённое состояние. Если соединение недоступно или занято отправкой,
клиент показывает ошибку, повторить действие можно нажатием E.

Новый или переподключившийся игрок получает текущий свет из первого снимка,
даже если его выключил другой участник. Отключение всех игроков не сбрасывает
объекты. После перезапуска backend свет снова включён; состояние хранится в памяти,
миграция БД не требуется. Неизвестный ID возвращает событие `command_rejected`
с кодом `object_not_found`, сохраняя WebSocket открытым.

Для разработки запускайте backend из корня проекта с автоматической перезагрузкой:

```bash
python -m uvicorn backend.main:app --host 0.0.0.0 --port 8000 --workers 1 --ws-max-size 4096 --reload --reload-dir backend
```

При перезагрузке процесса сессия сбрасывается, клиенты переподключаются. Без
`--reload` после изменений backend требуется ручной перезапуск, иначе старый
процесс может не поддерживать актуальные команды клиента.
